Three buckets, kept separate

Lumping every keyword hit into one number would be wrong: an unquoted search for “machine learning” also matches MEAL jobs (“Monitoring, Evaluation and Learning”), and “artificial intelligence” unquoted catches “Business Intelligence”. Quoted phrases only, then classified by where the phrase lands.

  • 55 title-flagged AI candidates. An AI phrase in the job title itself; all 55 titles reviewed at title level. A title match flags a likely AI role, but it is not proof the job is AI-centric; the linked posting is the check. Includes consultancies, internships, rosters and RFPs posted in the Jobs section.
  • 250 data roles with an AI mention. Title is a data-family job (analyst, scientist, information management, GIS, M&E, statistics) and the description mentions an AI phrase. Adjacent, not the same thing.
  • 999 other adverts mention AI somewhere in the text: anything from a core requirement to one line about tools. Never add these to an AI-jobs total.

How it’s run

The machine behind the numbers.

  1. The source.ReliefWeb’s Jobs API (v2), queried with an approved appname. A preset flag includes expired postings, which is what makes history possible: descriptions survive back to the oldest record, November 2009.
  2. The net.Nine quoted phrases across title and description: “artificial intelligence”, “machine learning”, “generative ai”, “large language model”, “chatgpt”, “natural language processing”, “deep learning”, “neural network”, “computer vision”. Quoting is the difference between signal and MEAL. The standalone token “AI” is not searched (too noisy), and non-English equivalents are not in the set, so non-English postings are undercounted.
  3. The sorting.Title match → title-flagged candidate, each title reviewed. Data-family title → data bucket. Anything else → mention-only. Each row keeps its matched phrases and the first excerpt around the match, so every call can be checked against the source.
  4. The dataset.Everything lands in a published Google Sheet: one tab per bucket, yearly counts, and the full methodology including the numerator/denominator definitions. The sheet is the dataset of record.
  5. This page.The charts are drawn from a snapshot of the sheet embedded in the page; the table above loads rows live from the sheet when it is reachable. A failed fetch shows the snapshot for the title-flagged bucket, never an empty page.

Keeping it currentOn · monthly

This dataset is refreshed automatically on the 1st of each month, using the same nine search phrases and API settings:

  1. Re-query.The ReliefWeb Jobs API is searched again, so late-added and revised postings are picked up.
  2. Deduplicate.Postings are matched by ReliefWeb job ID: existing rows are updated, never duplicated.
  3. Update.New rows go to the right bucket tabs in the sheet, the Yearly counts tab is recomputed, and the charts, annual table and “data pulled” date on this page are updated to match.
  4. Check.Each run is verified against the sheet and the annual table before the page changes; a failed run is reported, so a broken refresh looks broken, not fresh.

What this doesn’t show

  • Adverts, not outcomes: a posting is not a filled vacancy, a hire, or a distinct position. Reposts and rosters count separately.
  • Archive completeness is unverified: the API is the best available window, not a guarantee. Pre-2011 is thin, and the post-2022 drop in total adverts is unexplained.
  • Coverage is defined by the queries: nine English phrases, searched in title and description. Roles about AI written without these phrases, or in other languages, are missed. These are lower-bound counts, not a census of AI work.
  • The data bucket is defined the same way: data-family titles among the AI-phrase matches. It is not the universe of data jobs on ReliefWeb.
  • Mention-only rows range from “you will build our AI platform” to “comfortable with modern tools”. The excerpt column exists so nobody has to trust the bucket.
